 

1. **不要把陀螺仪、加速度计、重力传感器当成同一种东西。** 它们的测量含义不同，直接替换会改变交互手感。
2. **不要把传感器第一帧无条件当作水平基准。** 用户可能一开始就斜拿手机；基准会跟着错误姿势走，导致中立位漂移或不同用户体验不一致。
3. **不要只调灵敏度，不处理抖动、死区和滤波延迟。** 稳定与跟手是互相牵制的，滤波越重通常越迟钝。
4. **AGSL / RuntimeShader 不是“写出来就一定运行”。** 设备 GPU、系统版本、采样次数、坐标边界和着色器编译都可能影响结果。
5. **3D 旋转会缩短投影宽度，边缘露黑不是简单加大旋转角就能解决。** 拉伸补偿必须与折叠方向、采样映射一致。
6. **曲面重投影和 3D 平面旋转不是同一种模型。** 前者重新映射纹理，后者改变平面姿态；不要把两套公式混在一起。
7. **Android 横竖屏、显示旋转和传感器坐标轴必须一起考虑。** 只在单一竖屏设备调通，不代表其他方向正确。
8. **CI 通过不等于视觉效果通过。** Shader、帧率、边缘伪影和厂商传感器表现必须真机检查。

## 1. 传感器选择：Gravity、Accelerometer、Gyroscope

### 曾经的方案

早期实现优先使用 `传感器.TYPE_GRVITY`，注释中记录了选择理由：加速度计会包含设备自身运动产生的加速度，而 Gravity 是系统融合后的重力方向，通常更适合缓慢倾斜交互。

### 踩坑与边界

- `TYPE_ACCELEROMETER` 测量的是包含重力在内的设备加速度。手机走动、坐车、快速移动时，信号会混入线性运动。
- `TYPE_GRAVITY` 是系统估算的重力方向，通常更平滑，但它不是所有设备都保证提供的传感器。
- `TYPE_GYROSCOPE` 测量角速度，不是静态倾角。直接积分角速度会产生漂移；如果要用它，必须设计融合、重置和漂移控制。
- 不能仅因为项目叫 Gyroscope，就在实现里把所有传感器统称为陀螺仪。

### 当前工程要求

当前实现使用重力向量归一化，并有加速度计回退路径。后续若调整传感器来源，必须说明信号来源、坐标定义、采样频率、回退行为，并在真机验证。

## 2. 第一帧基准：看起来合理，实际可能错

### 早期做法

旧版在首次收到传感器事件时，把 `curX / curY` 记作 `baseX / baseY`，之后用当前值减去基准值作为倾斜量。

### 为什么会踩坑

第一帧不一定是用户想要的“水平姿势”。用户打开应用时可能已经倾斜手机，甚至在启动动画期间改变姿势。此时把第一帧锁定为中立位，会产生：
- 用户认为手机已经摆正，但效果仍偏向一侧；
- 重新进入页面后中立点发生变化；
- 不同启动姿势导致相同动作产生不同结果。

### 改进方向

不要静默假设第一帧就是水平。更稳妥的设计是明确中立位策略：使用重力方向计算相对倾角、提供重新校准入口，或在 UI 中告诉用户如何校准。校准必须可重复、可解释。

## 3. 灵敏度、平滑与死区：三者不能只看一个数

早期参数档案留下过这些经验起点：
- `TILT_FULL_SCALE = 16.0f`：将传感器变化映射到归一化输入；
- `TILT_SMOOTHING = 0.90f`：一阶低通平滑；
- `deadZone = 0f`：早期默认不启用死区；
- 最大旋转角约 `48°`。

这些值是历史调参起点，不是所有设备的最佳值，也不是已完成跨设备验证的结论。

### 典型问题

- 灵敏度太高：轻微手抖就触发明显动画。
- 灵敏度太低：用户需要大幅倾斜，交互显得迟钝。
- 平滑系数太大：画面稳定，但动作拖尾、跟手性差。
- 平滑系数太小：响应快，但画面抖动明显。
- 死区直接把数值归零：如果阈值边缘处理不连续，会产生跳变。
- 只在输入端做死区，不处理输出曲线：小幅动作和大幅动作的手感可能断层。

### 调参顺序

先确认传感器方向和零点，再调整输入范围，然后调整平滑，最后才调整死区与动画曲线。每次只改一个维度，并记录设备、系统版本、参数和观察结果。

## 4. AGSL / RuntimeShader：最危险的是“没有报错但没效果”

旧版实现包含三类 shader 思路：
- `HOME_BLUR_AGSL`：凹侧模糊与暗边；
- `CURVED_FOLD_AGSL`：曲面纹理重投影、明暗和局部模糊；
- `STRETCH_AGSL`：非线性横向拉伸补偿。

这些原始设计注释很有价值，但其中对采样上限、设备兼容和“实测”效果的描述必须视为历史经验，不能当成 Android 对所有设备的统一保证。

### 采样次数

旧版模糊使用 5×5 核，也就是最多 25 次邻域采样，另外还可能有中心采样。历史注释曾提醒 AGSL 对 `content.eval()` 调用存在设备相关限制。实际限制与 GPU、系统实现及 shader 结构有关，不应把“32～64 次”写成固定平台规范。

**经验：** 不要为了更强模糊无限增加采样点。优先减少采样、缩小模糊区域、降低分辨率或使用分层方案，并在多种 GPU 上验证。

### 坐标边界

旧版特别强调采样坐标需要 clamp 到图层边界。越界采样可能产生设备相关的未定义结果、边缘脏色或黑线。任何纹理重映射都要检查：
- 输入坐标是否在有效范围；
- 宽高是否可能为 0；
- 左右凹侧镜像后是否仍正确；
- 边缘 clamp 是否造成拉边或色带。

### Shader 编译与降级

不要只验证 Kotlin 编译成功。还要验证 RuntimeShader 在目标 Android 版本和实际 GPU 上成功创建并绘制。发生异常时应退回可用的普通 Compose 渲染，不要让整个页面空白或崩溃。

## 5. 3D 旋转为什么会露黑边

旧版设计的核心问题是：平面绕垂直边缘旋转后，投影宽度会缩短，边缘可能露出背景。

早期尝试使用非线性拉伸：凸侧尽量固定，向凹侧逐渐增加拉伸。旧档案中的起点包括：
- `MAX_TILT_DEGREES = 48f`
- `CAMERA_DISTANCE_FACTOR = 8f`
- `STRETCH_MAX = 1.6f`
- `STRETCH_EXPONENT = 1.5`

这些参数依赖布局尺寸、密度、相机距离和具体渲染方式，不能脱离上下文照搬。

### 常见错误

- 直接整体 scaleX：两侧一起变形，锚定边也会移动。
- 拉伸方向和凹侧方向不一致：左倾和右倾只有一边正确。
- 只在视觉上补宽度，不检查内容采样坐标：边缘可能被重复拉伸。
- 角度过大：即使补偿宽度，也可能出现夸张透视和内容压扁。

## 6. 曲面重投影：不要把它误认为真实折叠网格

旧版曲面思路是把屏幕内容按圆弧投影关系重新分布。注释中记录了映射关系：
- 折叠坐标 `p ∈ [0,1])；
- 最大弧角 `θ_max`；
- 投影位置与 `sin(θ)` 相关；
- 反解纹理坐标时使用 `asin`。

它的优势是可以让内容保持覆盖整个横向范围，减少 3D 平面旋转常见的边缘空洞；代价是纹理会非线性压缩，不能声称是真实物理屏幕弯曲。

**要验证的点：** 左右方向对称性、极端角度下纹理压缩、文字可读性、边缘连续性、模糊区域是否跟随凹侧。

## 7. 生命周期与耗电

传感器监听不应在应用后台无限运行。旧版在 Composable 退出时注销 listener；新工程进一步把监听绑定到 Activity 生命周期。

必须检查：
- 进入后台是否停止采样；
- 返回前台是否重新注册；
- 多次进入页面是否重复注册；
- 传感器不存在时是否进入手动模式；
- 释放监听后是否还在更新 Compose 状态。

## 8. 构建配置版本不匹配

早期工程使用过 Kotlin 1.9.22、Compose Compiler 1.5.10、AGP 8.2.2 一组版本。历史注释特别提醒 Compose Compiler 与 Kotlin 版本需要严格对应。

后来工程升级到 Kotlin 2.0.21 与 Compose 插件体系。不要把旧版本配置片段直接复制进新工程，也不要单独升级 Kotlin、AGP、Compose BOM 后就认为组合一定兼容。升级时以官方兼容矩阵和 CI 构建结果为准。

## 12. 原始 README 中的八条实战踩坑（逐条恢复）

以下八条来自项目早期 README 的原始“踩坑记录”章节。它们是项目历史经验，不应被后续重构覆盖。涉及旧版 API 行为的结论，应结合当前 Android / Compose 版本重新验证。

### 坑 1：AGSL 采样核过大，Shader 可能完全不生效

**原始现象：** 早期模糊尝试使用 9×9，共 81 次采样，最终画面没有模糊效果。

**当时的处理：** 把采样核降到 5×5，共 25 个邻域采样点，并通过调整采样半径弥补模糊强度。

**保留的经验：** Shader 的采样开销不能只看数学效果。采样次数、GPU 能力和设备实现都需要考虑。旧 README 提到的“32～64 次”是当时记录的经验范围，不是所有设备统一保证的硬性规格。大半径模糊优先考虑多 pass、降采样或更省采样的核。

### 坑 2：RenderEffect 需要离屏合成

**原始现象：** 仅给 `graphicsLayer` 设置 `renderEffect`，效果没有按预期出现。

**当时的处理：** 显式使用 `CompositingStrategy.Offscreen`，让内容先绘制到离屏图层，再应用 RenderEffect。

```kotlin
.graphicsLayer {
    compositingStrategy = CompositingStrategy.Offscreen
    renderEffect = effect
}
```

**保留的经验：** RenderEffect 的效果与图层合成路径有关。不要把“设置了 renderEffect 属性”当作“效果一定已经正确应用”。在当前 Compose 版本和目标设备上仍需验证。

### 坑 3：rotationY 与 RenderEffect 放在同一图层时发生冲突

**原始现象：** 早期把 3D 旋转和 Shader 效果放在同一个 graphicsLayer，实际效果中有一个处理被忽略。

**当时的处理：** 拆分嵌套图层：外层负责模糊，内层负责 rotationY，再内层负责拉伸或内容绘制。

**保留的经验：** 当多个图形变换、合成和 RenderEffect 叠加时，明确图层职责比堆 modifier 更可靠。具体限制随渲染实现变化，不能把旧设备上的现象写成所有 Compose 版本必然如此。

### 坑 4：3D 旋转导致凹侧露出黑底

**原始现象：** 使用 rotationY 倾斜后，投影宽度缩短，凹侧露出底层黑色背景。

**第一次尝试：** 使用均匀 scaleX 补偿宽度。

**副作用：** 凸侧也被拉宽，画面整体显得不自然。

**改进方向：** 改用非线性拉伸，让凸侧锚定、拉伸量逐渐集中到凹侧。旧版采用三次曲线作为实验方案。

### 坑 5：非线性拉伸的锚点必须跟随凸侧

旧版拉伸映射使用 `x' = x + c·x³/W²`，在 `x = 0` 处保持不动。因此必须先把坐标变换到“凸侧位于锚点”的统一坐标系。

**原始处理：** 根据 concaveSide 镜像坐标，完成映射后再镜像回去，避免左右方向维护两套公式。

**回归重点：** 左倾和右倾必须分别测试。只验证一侧，另一侧很容易出现拉伸方向反了、锚点跑错或边缘拉花。

### 坑 6：旋转轴分段切换会导致回正时画面震动

**原始现象：** 旧版用阈值判断旋转轴：正倾斜时锚在一边、负倾斜时锚在另一边、接近零时突然回到中心。倾斜值穿过阈值时，TransformOrigin 会跳变，画面出现明显“震一下”。

**当时的改进：** 把分段判断改成连续映射：

```kotlin
val originX = (0.5f - tiltX * 0.5f).coerceIn(0f, 1f)
```

这让旋转轴随 tiltX 连续变化，避免阈值处突然切换。

**保留的经验：** 动画的方向、锚点和参数映射尽量保持连续。阈值用于抑制噪声可以，但不应让视觉位置在阈值处突然跳跃。

### 坑 7：RenderEffect 挂载阈值附近反复开关，造成闪烁

**原始现象：** 旧版使用类似 `if (blurStrength > 0.01f)` 的条件决定是否挂载 Shader。输入在阈值附近抖动时，Shader 会不断挂载和卸载，画面出现闪烁。

**当时的改进：** 尽量保持 Shader 持续挂载，用 uniform 连续控制强度；避免让瞬时输入噪声决定昂贵渲染对象的生命周期。

**补充注意：** “一直挂载”也有性能成本。实际项目应比较持续挂载与阈值滞回/平滑启停的效果，不能为了避免闪烁而忽略低端设备性能。

### 坑 8：content.eval() 的采样坐标必须限制在有效范围

**原始现象：** 模糊采样点落到图层边界以外，可能出现边缘异常颜色。

**当时的处理：**

```glsl
float2 sampleCoord = clamp(
    xy + offset,
    float2(0.0),
    size
);
```

**保留的经验：** 任何邻域采样、纹理重映射或镜像变换，都要检查边界。还要注意 size 为零、坐标单位与像素密度、最右/最下边界的取值规则，避免只修复普通区域却留下边缘伪影。

## 13. 原始兼容性策略：AGSL 降级不是可选装饰

早期 README 记录了以下兼容策略：
- AGSL / RuntimeShader 路径从 Android 13（API 33）开始使用。
- Android 12 / 12L（API 31～32）使用 RenderEffect 的普通模糊作为有限降级。
- 更低版本不使用 RuntimeShader 路径，回退到基础画面。

这是一条历史实现路线，不代表当前工程已经完整复刻了旧版的每一种降级效果。后续若调整 minSdk 或渲染实现，必须检查 API 级别判断、设备 GPU 支持和无 Shader 时的可用 UI。

旧版集成说明还强调了三件事：

2. 对 RenderEffect 路径检查 Offscreen 合成。
3. 不要把早期演示工程的文件直接覆盖进当前模块；当前工程的 Activity、传感器生命周期和 Compose 依赖已经重新组织。
