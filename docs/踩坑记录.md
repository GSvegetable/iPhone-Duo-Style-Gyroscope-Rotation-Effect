0. 快速结论与禁止事项

0.1 快速结论

1. 陀螺仪、加速度计、重力传感器不是同一种东西。 测量含义不同，直接替换会改变交互手感。
2. 不要把传感器第一帧无条件当作水平基准。 用户可能一开始就斜拿手机，基准会跟着错误姿势走。
3. 灵敏度、平滑、死区、滤波延迟要一起调。 稳定与跟手互相牵制，滤波越重通常越迟钝。
4. AGSL / RuntimeShader 不是“写出来就一定运行”。 GPU、系统版本、采样次数、坐标边界和编译都可能影响结果。
5. 3D 旋转会缩短投影宽度，边缘露黑不是简单加大旋转角就能解决。 拉伸补偿必须与折叠方向、采样映射一致。
6. 曲面重投影和 3D 平面旋转不是同一种模型。 前者重新映射纹理，后者改变平面姿态，不能混用公式。
7. 横竖屏、显示旋转和传感器坐标轴必须一起考虑。 单一竖屏调通不代表其他方向正确。
8. CI 通过不等于视觉效果通过。 Shader、帧率、边缘伪影和厂商传感器表现必须真机检查。
9. 图形变换要拆图层。 rotationY、RenderEffect、拉伸补偿放在同一图层容易冲突，应明确图层职责。
10. 连续性优先。 旋转轴、锚点、Shader 挂载状态尽量避免在阈值处突然跳变。
11. Shader 必须有降级路径。 RuntimeShader 创建或绘制异常时，应退回普通 Compose 渲染，不能白屏或崩溃。
12. 没测过就不要写“已验证”。 真机清单中的项目必须逐项记录设备和结果。

0.2 禁止事项

· 禁止把 Gyroscope、Accelerometer、Gravity 在代码和文档中统称为“陀螺仪”。
· 禁止静默把第一帧传感器值当作水平基准。
· 禁止只调灵敏度，不处理抖动、死区和滤波延迟。
· 禁止把旧参数表直接复制到新设备、新布局或新密度环境。
· 禁止在纹理重映射中省略边界 clamp 和 size 非零检查。
· 禁止把“Kotlin 编译通过”或“CI 通过”当作 Shader 视觉通过。
· 禁止把旧版 Compose / Kotlin / AGP 配置片段直接复制进新工程。
· 禁止在未真机验证时把历史结论写成平台统一保证。

2. 传感器选择：Gravity、Accelerometer、Gyroscope

2.1 早期方案

早期实现优先使用 Sensor.TYPE_GRAVITY。选择理由是：加速度计会包含设备自身运动产生的加速度，而 Gravity 是系统融合后的重力方向，通常更适合缓慢倾斜交互。

2.2 踩坑与边界

· TYPE_ACCELEROMETER 测量包含重力在内的设备加速度。手机走动、坐车、快速移动时，信号会混入线性运动。
· TYPE_GRAVITY 通常更平滑，但不是所有设备都保证提供。
· TYPE_GYROSCOPE 测量角速度，不是静态倾角。直接积分角速度会产生漂移；如果要用它，必须设计融合、重置和漂移控制。
· 不能仅因为项目叫 Gyroscope，就在实现里把所有传感器统称为陀螺仪。

2.3 当前工程要求

当前实现使用重力向量归一化，并有加速度计回退路径。后续若调整传感器来源，必须说明：

· 信号来源；
· 坐标定义；
· 采样频率；
· 回退行为；
· 真机验证结果。

3. 第一帧基准与中立位策略

3.1 早期做法

旧版在首次收到传感器事件时，把 curX / curY 记作 baseX / baseY，之后用当前值减去基准值作为倾斜量。

3.2 为什么会踩坑

第一帧不一定是用户想要的“水平姿势”。用户打开应用时可能已经倾斜手机，甚至在启动动画期间改变姿势。此时把第一帧锁定为中立位，会产生：

· 用户认为手机已经摆正，但效果仍偏向一侧；
· 重新进入页面后中立点发生变化；
· 不同启动姿势导致相同动作产生不同结果。

3.3 改进方向

不要静默假设第一帧就是水平。更稳妥的设计是明确中立位策略：

· 使用重力方向计算相对倾角；
· 提供重新校准入口；
· 在 UI 中告诉用户如何校准；
· 校准必须可重复、可解释。

4. 灵敏度、平滑与死区

4.1 历史参数起点

早期参数档案留下过这些经验起点：

· TILT_FULL_SCALE = 16.0f：将传感器变化映射到归一化输入；
· TILT_SMOOTHING = 0.90f：一阶低通平滑；
· deadZone = 0f：早期默认不启用死区；
· 最大旋转角约 48°。

这些值是历史调参起点，不是所有设备的最佳值，也不是已完成跨设备验证的结论。

4.2 典型问题

· 灵敏度太高：轻微手抖就触发明显动画。
· 灵敏度太低：用户需要大幅倾斜，交互显得迟钝。
· 平滑系数太大：画面稳定，但动作拖尾、跟手性差。
· 平滑系数太小：响应快，但画面抖动明显。
· 死区直接把数值归零：如果阈值边缘处理不连续，会产生跳变。
· 只在输入端做死区，不处理输出曲线：小幅动作和大幅动作的手感可能断层。

4.3 调参顺序

1. 先确认传感器方向和零点；
2. 再调整输入范围；
3. 然后调整平滑；
4. 最后调整死区与动画曲线。

每次只改一个维度，并记录设备、系统版本、参数和观察结果。

4.4 建议补充的量化验收指标（待确认）

以下指标用于后续真机验证，不是当前已验证结论：

· 回中误差范围；
· 连续倾斜 10 秒的漂移上限；
· 快速晃动时的最大跳变；
· 目标帧率下限；
· 每帧 Shader 采样预算；
· 模糊区域最大尺寸与离屏层数上限。

5. AGSL / RuntimeShader：最危险的是“没有报错但没效果”

旧版实现包含三类 Shader 思路：

· HOME_BLUR_AGSL：凹侧模糊与暗边；
· CURVED_FOLD_AGSL：曲面纹理重投影、明暗和局部模糊；
· STRETCH_AGSL：非线性横向拉伸补偿。

这些原始设计注释很有价值，但其中对采样上限、设备兼容和“实测”效果的描述必须视为历史经验，不能当成 Android 对所有设备的统一保证。

5.1 采样次数

旧版模糊使用 5×5 核，即最多 25 次邻域采样，另外还可能有中心采样。历史注释曾提醒 AGSL 对 content.eval() 调用存在设备相关限制。实际限制与 GPU、系统实现及 Shader 结构有关，不应把“32～64 次”写成固定平台规范。

经验：

· 不要为了更强模糊无限增加采样点。
· 优先减少采样、缩小模糊区域、降低分辨率或使用分层方案。
· 大半径模糊优先考虑多 pass、降采样或更省采样的核。
· 必须在多种 GPU 上验证。

5.2 坐标边界

旧版特别强调采样坐标需要 clamp 到图层边界。越界采样可能产生设备相关的未定义结果、边缘脏色或黑线。任何纹理重映射都要检查：

· 输入坐标是否在有效范围；
· 宽高是否可能为 0；
· 左右凹侧镜像后是否仍正确；
· 边缘 clamp 是否造成拉边或色带；
· 最右/最下边界的取值规则是否与像素坐标规则一致。

示例：

```glsl
float2 sampleCoord = clamp(
    xy + offset,
    float2(0.0),
    size
);
```

5.3 Shader 编译与降级

不要只验证 Kotlin 编译成功。还要验证 RuntimeShader 在目标 Android 版本和实际 GPU 上成功创建并绘制。

建议实现（待确认）：

· RuntimeShader 创建和绘制使用异常捕获；
· 发生异常时退回可用的普通 Compose 渲染；
· 不要让整个页面空白或崩溃；
· 首次使用可记录 GPU / Shader 能力日志；
· 降级后的视觉差异应有说明。

6. 3D 旋转为什么会露黑边

旧版设计的核心问题是：平面绕垂直边缘旋转后，投影宽度会缩短，边缘可能露出背景。

早期尝试使用非线性拉伸：凸侧尽量固定，向凹侧逐渐增加拉伸。旧档案中的起点包括：

· MAX_TILT_DEGREES = 48f
· CAMERA_DISTANCE_FACTOR = 8f
· STRETCH_MAX = 1.6f
· STRETCH_EXPONENT = 1.5

这些参数依赖布局尺寸、密度、相机距离和具体渲染方式，不能脱离上下文照搬。

6.1 常见错误

· 直接整体 scaleX：两侧一起变形，锚定边也会移动。
· 拉伸方向和凹侧方向不一致：左倾和右倾只有一边正确。
· 只在视觉上补宽度，不检查内容采样坐标：边缘可能被重复拉伸。
· 角度过大：即使补偿宽度，也可能出现夸张透视和内容压扁。

6.2 非线性拉伸锚点

旧版拉伸映射使用：

```text
x' = x + c · x³ / W²
```

在 x = 0 处保持不动。因此必须先把坐标变换到“凸侧位于锚点”的统一坐标系。

原始处理：根据 concaveSide 镜像坐标，完成映射后再镜像回去，避免左右方向维护两套公式。

回归重点：左倾和右倾必须分别测试。只验证一侧，另一侧很容易出现拉伸方向反了、锚点跑错或边缘拉花。

6.3 旋转轴连续性

旧版用阈值判断旋转轴：正倾斜时锚在一边、负倾斜时锚在另一边、接近零时突然回到中心。倾斜值穿过阈值时，TransformOrigin 会跳变，画面出现明显“震一下”。

改进为连续映射：

```kotlin
val originX = (0.5f - tiltX * 0.5f).coerceIn(0f, 1f)
```

这让旋转轴随 tiltX 连续变化，避免阈值处突然切换。

保留经验：动画的方向、锚点和参数映射尽量保持连续。阈值用于抑制噪声可以，但不应让视觉位置在阈值处突然跳跃。

7. 曲面重投影：不要误认为真实折叠网格

旧版曲面思路是把屏幕内容按圆弧投影关系重新分布。注释中记录了映射关系：

· 折叠坐标 p ∈ [0,1)；
· 最大弧角 θ_max；
· 投影位置与 sin(θ) 相关；
· 反解纹理坐标时使用 asin。

它的优势是可以让内容保持覆盖整个横向范围，减少 3D 平面旋转常见的边缘空洞；代价是纹理会非线性压缩，不能声称是真实物理屏幕弯曲。

要验证的点：

· 左右方向对称性；
· 极端角度下纹理压缩；
· 文字可读性；
· 边缘连续性；
· 模糊区域是否跟随凹侧。

8. 图层职责与 RenderEffect

8.1 RenderEffect 需要离屏合成

原始现象：仅给 graphicsLayer 设置 renderEffect，效果没有按预期出现。

当时处理：显式使用 CompositingStrategy.Offscreen，让内容先绘制到离屏图层，再应用 RenderEffect。

```kotlin
.graphicsLayer {
    compositingStrategy = CompositingStrategy.Offscreen
    renderEffect = effect
}
```

保留经验：RenderEffect 的效果与图层合成路径有关。不要把“设置了 renderEffect 属性”当作“效果一定已经正确应用”。在当前 Compose 版本和目标设备上仍需验证。

8.2 rotationY 与 RenderEffect 同层冲突

原始现象：早期把 3D 旋转和 Shader 效果放在同一个 graphicsLayer，实际效果中有一个处理被忽略。

当时处理：拆分嵌套图层：

· 外层负责模糊；
· 内层负责 rotationY；
· 再内层负责拉伸或内容绘制。

保留经验：当多个图形变换、合成和 RenderEffect 叠加时，明确图层职责比堆 modifier 更可靠。具体限制随渲染实现变化，不能把旧设备上的现象写成所有 Compose 版本必然如此。

8.3 RenderEffect 阈值闪烁

原始现象：旧版使用类似 if (blurStrength > 0.01f) 的条件决定是否挂载 Shader。输入在阈值附近抖动时，Shader 会不断挂载和卸载，画面出现闪烁。

当时改进：尽量保持 Shader 持续挂载，用 uniform 连续控制强度；避免让瞬时输入噪声决定昂贵渲染对象的生命周期。

补充注意：“一直挂载”也有性能成本。实际项目应比较持续挂载与阈值滞回/平滑启停的效果，不能为了避免闪烁而忽略低端设备性能。

9. 生命周期与耗电

传感器监听不应在应用后台无限运行。旧版在 Composable 退出时注销 listener；新工程进一步把监听绑定到 Activity 生命周期。

必须检查：

· 进入后台是否停止采样；
· 返回前台是否重新注册；
· 多次进入页面是否重复注册；
· 传感器不存在时是否进入手动模式；
· 释放监听后是否还在更新 Compose 状态。

10. 构建配置版本不匹配

早期工程使用过 Kotlin 1.9.22、Compose Compiler 1.5.10、AGP 8.2.2 一组版本。历史注释特别提醒 Compose Compiler 与 Kotlin 版本需要严格对应。

后来工程升级到 Kotlin 2.0.21 与 Compose 插件体系。不要把旧版本配置片段直接复制进新工程，也不要单独升级 Kotlin、AGP、Compose BOM 后就认为组合一定兼容。升级时以官方兼容矩阵和 CI 构建结果为准。

11. 兼容性与降级策略

早期 README 记录了以下兼容策略：

· AGSL / RuntimeShader 路径从 Android 13（API 33）开始使用。
· Android 12 / 12L（API 31～32）使用 RenderEffect 的普通模糊作为有限降级。
· 更低版本不使用 RuntimeShader 路径，回退到基础画面。

这是一条历史实现路线，不代表当前工程已经完整复刻旧版的每一种降级效果。后续若调整 minSdk 或渲染实现，必须检查：

· API 级别判断；
· 设备 GPU 支持；
· RuntimeShader 创建和绘制异常；
· 无 Shader 时的可用 UI；
· 降级后的视觉差异说明；
· 线上或本地日志字段。

14. 历史八坑索引（保留原始经验）

以下八条来自项目早期 README 的原始“踩坑记录”章节。它们是项目历史经验，不应被后续重构覆盖。涉及旧版 API 行为的结论，应结合当前 Android / Compose 版本重新验证。

编号 原始现象 当时处理 保留经验
坑 1 早期模糊尝试使用 9×9，共 81 次采样，最终画面没有模糊效果 把采样核降到 5×5，共 25 个邻域采样点，并通过调整采样半径弥补模糊强度 Shader 采样开销不能只看数学效果；大半径模糊优先考虑多 pass、降采样或更省采样的核；“32～64 次”是历史经验范围，不是平台硬规格
坑 2 仅给 graphicsLayer 设置 renderEffect，效果没有按预期出现 显式使用 CompositingStrategy.Offscreen RenderEffect 与图层合成路径有关，不能把“设置了属性”当作“效果已正确应用”
坑 3 把 3D 旋转和 Shader 效果放在同一个 graphicsLayer，实际效果中有一个处理被忽略 拆分嵌套图层：外层模糊、内层 rotationY、再内层拉伸或内容绘制 多个图形变换、合成和 RenderEffect 叠加时，明确图层职责比堆 modifier 更可靠；旧设备现象不能写成所有 Compose 版本必然
坑 4 使用 rotationY 倾斜后，投影宽度缩短，凹侧露出底层黑色背景 第一次尝试均匀 scaleX 补偿宽度，副作用是凸侧也被拉宽；改进方向是非线性拉伸，凸侧锚定、拉伸量逐渐集中到凹侧 3D 旋转露黑边不能只靠整体放大解决；拉伸补偿必须与折叠方向和采样映射一致
坑 5 非线性拉伸锚点必须跟随凸侧 旧版拉伸映射使用 x' = x + c·x³/W²，在 x = 0 处保持不动；根据 concaveSide 镜像坐标，完成映射后再镜像回去 左倾和右倾必须分别测试；只验证一侧，另一侧容易拉伸方向反了、锚点跑错或边缘拉花
坑 6 旧版用阈值判断旋转轴，倾斜值穿过阈值时 TransformOrigin 跳变，画面“震一下” 改成连续映射：originX = (0.5f - tiltX * 0.5f).coerceIn(0f, 1f) 动画方向、锚点和参数映射尽量连续；阈值可用于抑制噪声，但不应让视觉位置突然跳跃
坑 7 使用 if (blurStrength > 0.01f) 决定是否挂载 Shader，输入在阈值附近抖动时 Shader 反复挂载/卸载，画面闪烁 尽量保持 Shader 持续挂载，用 uniform 连续控制强度 避免让瞬时输入噪声决定昂贵渲染对象的生命周期；“一直挂载”也有性能成本，应比较持续挂载与阈值滞回/平滑启停
坑 8 模糊采样点落到图层边界以外，可能出现边缘异常颜色 使用 clamp(xy + offset, float2(0.0), size) 任何邻域采样、纹理重映射或镜像变换都要检查边界；还要注意 size 为零、坐标单位与像素密度、最右/最下边界取值规则
